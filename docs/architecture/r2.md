# Cloudflare R2: the read copy of weft-blobs

Status: code built and `blob_mirror` applied (version 20261029105650) on 2026-10-29. Waiting on: R2 switched on for the
Cloudflare account, the bucket and its token, and the backfill.

## Why

Synced blobs (screenshots, pasted images, mini app pages and files) live in the Supabase Storage bucket `weft-blobs`,
content-addressed as `<org_id>/<sha256>` (docs/architecture/cloud-sync.md#the-weft-blobs-storage-bucket): ~4,500
objects, 264 MB on 2026-10-29. Supabase's free plan allows 5 GB of egress a month, and every signed-URL read is a CDN
MISS, billed in full. On 2026-10-28 a share page re-signing a thumbnail every 4 s burned 1.6 GB in a day (fixed in
de93cab). Normal traffic is ~8 MB a day, but a popular share page would hit the cap. R2 charges nothing for egress.

## The shape

**Supabase stays where blobs are written. R2 is a copy that serves the reads.**

```
desktop outbox ──upload (RLS: insert as member)──▶ Supabase weft-blobs   (source of truth, unchanged)
                                                        │
                    lib/r2-mirror.ts: download once, PUT, insert blob_mirror row
                                                        ▼
                                                   R2 weft-blobs        (read copy, 0 egress)
readers ── lib/blob-urls.ts / lib/blob-read.ts ──▶ R2 if blob_mirror has the row, else Supabase (and queue the copy)
```

Why not move writes too: uploads cost no egress, the bucket's RLS already gates who may write, and the installed
desktop apps would keep uploading to Supabase until they updated. A mirror needs no desktop change at all.

### Auth: presigned S3 URLs

The server runs the same access check it runs today, then signs a SigV4 GET URL
(`https://<account>.r2.cloudflarestorage.com/weft-blobs/<org>/<sha>?X-Amz-…`). The URL is the only check R2 makes.

- **Web board** (`app/[orgSlug]/board/page.tsx`, `components/web-board/useWebBoard.ts`): the visitor's own session reads
  `blob_mirror`, whose select policy is `private.is_org_member(org_id)`. So a row coming back *is* the membership check,
  and only then is an R2 URL signed. The browser can't sign R2 URLs itself, so `useWebBoard` asks
  `POST /api/web-board/[orgId]/blob-urls` (same session, max 200 refs). When that route fails, it falls back to its own
  Supabase signing.
- **Share pages** (`lib/share-live.ts`): the service client, after the share's own access check, as before.
- **Server byte reads** (`lib/share-page-serve.ts` for share and mini app pages and files, `lib/app-share-meta.ts` for
  preview images, `app/api/web-board/[orgId]/page/[sha]`): `readBlob` tries R2's GetObject first and falls back to
  Supabase on a miss. The web-board pane route checks `blob_mirror` with the visitor's session before it reads R2.
  Otherwise the service-keyed R2 read would skip the bucket's member policy.
- The desktop's own `fetchBlob` (`lib/blob-store.ts`) still reads Supabase. It's a cache on the Mac and rare.

**Signing at the top of the hour.** `presignGet` signs with the hour's start as its date and a 2 h lifetime, so a
blob's URL stays the same for an hour and the browser cache works across page loads. Every URL is valid for at
least an hour. The objects are written with `Cache-Control: private, max-age=31536000, immutable`, since a content
hash never changes.

The alternative was a Worker on `blobs.weft.zip` checking an HMAC token, with CDN caching. It wasn't chosen because
weft.zip's DNS is on Vercel (a custom R2/Worker domain needs the zone on Cloudflare), it adds a second deploy
target, and it puts the auth rules in two places. R2 reads cost $0.36 per million past 10 M a month, so the lack of
a CDN cache in front costs nothing now.

No SDK: `lib/r2.ts` is SigV4 over `node:crypto`, and `lib/r2.test.ts` pins its signatures to the `aws4` package's for
the same requests.

## Pieces

| File | What |
|---|---|
| `lib/r2.ts` | `r2Config()` from `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` (default `weft-blobs`); `presignGet`, `signedHeaders`, `r2Put`, `r2Get` |
| `lib/blob-urls.ts` | `resolveBlobUrls(client, orgId, refs, { onUnmirrored })`: R2 for mirrored shas, Supabase signed URLs for the rest. Replaced three copies of the same `createSignedUrls` loop |
| `lib/blob-read.ts` | `readBlob(client, orgId, sha)`: bytes and type, R2 first |
| `lib/r2-mirror.ts` | `mirrorOne`, `mirrorPending` (drain `blob_mirror_pending()`, 8 at a time, 240 s budget, stops after 3 batches in a row copy nothing), `mirrorShas` |
| `lib/r2-queue.ts` | `queueMirror(orgId)`: the `onUnmirrored` hook; copies after the response with `next/server` `after()` |
| `app/api/cron/r2-mirror` | daily sweep (`vercel.json`, 03:30 UTC, `CRON_SECRET`) for blobs nobody has opened |
| `scripts/r2-backfill.ts` | `pnpm r2:backfill`: the one-time copy, resumable |
| `supabase/migrations/20261029105650_blob_mirror.sql` | `blob_mirror (org_id, sha, bytes, mirrored_at)`, members read, service writes; `blob_mirror_pending(max_rows)` and `blob_mirror_stats()`, service role only |

New blobs move within a request or two: the first read that falls back to Supabase queues the copy. The daily cron
catches the rest. A Supabase download per copy is the only egress the mirror costs, once per object.

## Setup and migration

1. Cloudflare dashboard → R2 → enable (it needs a payment method; the free tier is 10 GB stored, 1 M writes and
   10 M reads a month). `cf r2 buckets list` answered `10042 Please enable R2` on 2026-10-29.
2. Create bucket `weft-blobs` (`cf r2 buckets create`), then an API token: R2 → Manage API tokens → Object Read &
   Write on that one bucket.
3. Fill the 🔐 blanks (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`, development and
   production) and push them to Vercel (`mcp__secrets__push_to_vercel`).
4. Apply the `blob_mirror` migration (done 2026-10-29). Without it, `mirroredShas` reads nothing and every reader stays on Supabase.
5. Backfill: `mcp__secrets__run("pnpm r2:backfill", [SUPABASE_SECRET_KEY, R2_*])`. It copies ~264 MB once (that
   much Supabase egress, one time) and prints `blob_mirror_stats()`.
6. Cut-over happens per object: a blob is read from R2 the moment its row lands. Nothing is switched globally.

**Fallback.** Supabase keeps every object and nothing is ever deleted from it. A blob without a row, or an R2 read
that fails, is served from Supabase.

**Rollback.** Set `WEFT_BLOBS_R2=off` (or unset the `R2_*` values) on Vercel and redeploy. Every reader goes back to
Supabase signed URLs, with no data to move. Dropping R2 for good: delete the bucket and `truncate blob_mirror`.

**Retiring Supabase storage** (later, not built): once R2 has served for a while, uploads could go to R2 through a
presigned PUT from a weft.zip route, with Supabase kept only for old desktop builds.

## The infra dashboard

`GET /api/infra/live` also reads `public.blob_mirror_stats()` (`readR2Live` in `lib/infra-live.ts`). The providers
table shows Cloudflare R2 as **live · N objects, X MB · M to copy** once anything is copied, and "not used" before
that. The quotas table gains an **R2 storage** row against the 10 GB free tier. Supabase's egress row should then
fall toward the upload-only baseline. Not built: R2's own operation counts (Class A/B) from Cloudflare's GraphQL
`r2OperationsAdaptiveGroups`.
